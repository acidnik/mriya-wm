# Архитектура Mriya WM

Документ описывает текущее состояние кода. Цели проекта — в [README](../README.md).

## Что уже работает

### Итерация 1 — вложенная сессия

- Композитор запускается **вложенно** (nested): окно внутри текущей Wayland-сессии,
  как `niri --nested`. Никакого доступа к DRM/udev пока не нужно.
- Поднимается собственный Wayland-сокет (`wayland-N`), клиенты подключаются к нему.
- Поддерживаются протоколы: `wl_compositor`, `wl_subcompositor`, `wl_shm`,
  `xdg_wm_base` (toplevel + popup), `wl_seat` (клавиатура и указатель),
  `wl_output` + `zxdg_output_manager_v1`, `wl_data_device` (copy/paste, drag&drop).
- Окна отображаются без серверных декораций (SSD нет, клиенты рисуют свои CSD).
- Размещение новых окон — каскадом от левого верхнего угла (см. `src/shell.rs`).
- Рендер: `GlesRenderer` (EGL/GLES2), кадр рисуется по требованию
  (когда сцена изменилась), а не постоянным циклом.

### Итерация 7 — SSD, этап D (текст, правила, тени)

- **Текст заголовка** рисуется cosmic-text в текстуру заголовка: шрифт из
  `decorations { title-font "Sans Bold 9" }` (как в xfwm4 — это настройка WM, а
  не темы; размер в пунктах переводится в пиксели), `title_alignment`,
  `title_horizontal_offset`, `title_vertical_offset_active/inactive`, цвета
  `active/inactive_text_color`, тени `title_shadow_*` (`true` — под текстом,
  `frame` — обводка с четырёх сторон). Текст обрезается областью между
  заголовочными капсами `title-2`/`title-4`, как в `frameCreateTitlePixmap`.
- **`window-rule`** в конфиге: `match app-id=` / `match title=` (регулярные
  выражения, несколько `match` внутри правила — ИЛИ, последнее подходящее
  правило побеждает) и `decorations "client-side" | "server-side"`. Правило
  перекрывает запрос клиента по `xdg-decoration`, поэтому GTK4-приложениям
  можно не рисовать вторую рамку.
- **Тени** по `shadow_opacity`: силуэт кадра (все непрозрачные пиксели),
  уменьшенный в 4 раза, размывается тремя проходами box-blur и рисуется под
  кадром. Уменьшение — чтобы пересборка на каждый шаг интерактивного ресайза
  оставалась дешёвой. `shadow_delta_*` пока не применяются (тень
  центрированная).
- Иконка приложения (`show_app_icon`) не сделана: в Wayland у толевела нет
  иконки, её пришлось бы искать по app-id → `.desktop` → теме иконок (плюс
  SVG), это отдельная задача.

### Итерация 6 — SSD, этап C (рендер темы)

- Кадр собирается из частей темы (`src/decor/frame.rs`), как в xfwm4:
  - **заголовок** — полоса между верхними углами; при наличии
    `title-*-stretch` растягивается, иначе тайлится из `title-1…title-5`
    (капсы `title-1`/`title-5` дотягиваются до групп кнопок);
  - **бордеры** растягиваются вдоль своей длинной оси (в темах это градиенты);
  - **углы** рисуются поверх, в своих натуральных размерах;
  - **кнопки** располагаются по `button_layout` (буквы до `|` — слева, после —
    справа, последняя буква правой группы самая правая), с картинками
    `-active/-inactive/-prelight/-pressed` и `-toggled-*` для развёрнутых окон.
- Готовые текстуры кэшируются **на окно** с ключом (размер, активно/нет,
  maximized, hover, pressed) и пересобираются только при изменении ключа.
  Загрузка в GPU — premultiplied ARGB.
- **Маска прозрачности**: для каждой части строится 1 бит на пиксель; точка
  рамки считается непрозрачной только если там реально что-то нарисовано.
  Поэтому скруглённые углы и пустые места кнопок «прозрачны» для кликов — клик
  уходит окну ниже (проверено: клик по прозрачному углу снимает фокус, клик по
  заголовку рядом — ставит).
- Если тема не найдена — предупреждение со списком доступных тем и плоская
  рамка (композитор остаётся работоспособным).
- Проверено на `Default`: синий активный заголовок, серый неактивный, кнопки
  minimize/maximize/close из темы, hover/pressed меняют картинку (диф
  скриншотов показывает изменение ровно в прямоугольнике кнопки).
- Не сделано в этом этапе: текст заголовка (D), тени `shadow_delta_*` (D),
  кнопки `menu`/`shade`/`stick` (нет действий), полоса `top-N` (её нет ни в
  одной из установленных тем).

### Итерация 5 — SSD, этап B (загрузчик тем xfwm4)

- Тема = каталог `<name>/xfwm4` с `themerc` и картинками частей. Ищется в
  `~/.themes`, `~/.local/share/themes`, `$XDG_DATA_HOME/themes` и
  `$XDG_DATA_DIRS/themes`. Выбор: `decorations { theme "Default" }`,
  список доступных — `mriya-wm --list-themes`.
- **XPM обязателен**: 75 из 99 тем в системе поставляются только в XPM. Свой
  декодер поддерживает `s <symbol>` (символьные цвета), `c #rrggbb`, `None`,
  имена цветов (`gray50` и т.п.) и `chars_per_pixel` 1 или 2.
- **PNG накладывается поверх XPM** (`ThemeImage::over`), как
  `xfwmPixmapCompose` в xfwm4: XPM даёт форму и цвета, PNG — сглаживание. В
  `Default` PNG полностью прозрачный, в `Default-4.8` — несёт полупрозрачные
  края.
- **Палитра** из 24 символов (`active_color_2`, `active_hilight_1`, ...):
  xfwm4 берёт их из GTK-темы, у нас — встроенный пресет и оверрайды в
  `decorations { palette { ... } }`. Ссылки внутри `themerc`
  (`active_text_color=active_text_color_2`) разворачиваются транзитивно.
- **Геометрия кадра теперь из темы**: высота заголовка из
  `title-3-active`/`title-active-stretch`, ширины бордеров из
  `left/right/bottom-active` (или `*-stretch`). Для `Default` это 29 px и 5 px.
  Фолбэк без темы — прежние 28/4.
- Проверено: загружаются **все 99** тем из `/usr/share/themes`, у каждой есть
  высота заголовка; `Default` → 60 частей, 29 px заголовок, бордеры 5/5/5;
  `Alternate` (xpm-only, символьные цвета) → 51 часть, 22 px, 7/7/7.
- Отрисовка пока плоская (этап C): цвета-заглушки, но уже в размерах темы.

### Итерация 4 — SSD, этап A (рамка без темы)

- Реализован `zxdg_decoration_manager_v1`. Политика: **рамку рисуем всем**
  толевелам, но явный запрос клиента на `ClientSide` уважаем. Клиенты, которые
  протокол не реализуют (kitty), просто получают нашу рамку без двойных
  декораций; GTK4-приложения с собственным CSD получат две рамки — это
  вылечится правилами по `app-id` в следующей итерации.
- Рамка: заголовок 28 px, рамка 4 px, кнопки close (красная) и maximize
  (синяя) справа, hover/pressed состояния. Цвета — заглушка, тема xfwm4 будет
  на этапе B/C.
- Модель: **расположение окна в `Space` = расположение его контента**; рамка
  рисуется вокруг (вверх и влево от контента). Поэтому вся логика каскада,
  грабов и `Space` осталась нетронутой, а рамка живёт в отдельном слое
  отрисовки.
- Рамка учитывается в геометрии: при maximize контент получает размер
  «вывод минус рамка/заголовок» (`borderless_maximize`, как в xfwm4: боковые и
  нижняя рамки исчезают, заголовок остаётся), при fullscreen рамки нет вообще.
- Ввод: клик по заголовку — move-grab, двойной клик — maximize, клик по краю —
  resize-grab, кнопки — close/maximize (действие по release, если курсор всё
  ещё над кнопкой). Ввод по контенту уходит клиенту как раньше.
- Состояние окна (режим декораций, активно/развёрнуто/фуллскрин, заголовок,
  app-id, hover/pressed) лежит в user data окна, как в anvil.

### Итерация 3 — конфиг в kdl

- Конфиг: `$XDG_CONFIG_HOME/mriya/config.kdl` (обычно `~/.config/mriya/config.kdl`)
  или `--config <path>`. Секции и синтаксис — **как в niri**, чтобы конфиг можно
  было скопировать: незнакомые секции/опции/действия не ломают разбор, а
  пропускаются с сообщением в лог (`RUST_LOG=mriya_wm=debug`).
- Работают: `cursor { xcursor-theme, xcursor-size }`,
  `input { keyboard { xkb { rules/model/layout/variant/options }, repeat-delay,
  repeat-rate } }`, `environment { KEY "value" }`, `spawn-at-startup` и
  `binds { ... }`.
- Действия в `binds`: `close-window`, `quit`, `fullscreen-window`,
  `maximize-window`, `spawn "cmd" args...`, `spawn-sh "командная строка"`.
  Хоткеи работают в любой раскладке: привязка ищется по US-keysym нажатой
  клавиши, а не по текущей раскладке.
- `Mod` как в niri: во вложенном режиме это `Alt` (родительская сессия обычно
  держит `Super`), на TTY будет `Super`.
- `spawn-at-startup`: одна строка — запускается через `sh -c`, несколько
  аргументов — напрямую. Дети получают наш `WAYLAND_DISPLAY` и
  переиспользуются/переподхватываются (`reap`) без зомби.
- Ошибка в конфиге: пишем предупреждение и работаем на дефолтах.

### Итерация 2 — курсор и частичный урон

- **Курсор рисует сам композитор**: иконки из XCursor-темы
  (`XCURSOR_THEME` / `XCURSOR_SIZE`, по умолчанию `default` и 24) для именованных
  курсоров и клиентские `wl_cursor.set_cursor` поверхности — с учётом hotspot.
- Курсор родительской сессии над нашим окном **скрыт**
  (`winit` `set_cursor_visible(false)`), чтобы не было двух стрелок.
  Если тема не загрузилась, курсор хоста остаётся как fallback.
- **Частичный урон**: кадр рисуется только в изменившихся прямоугольниках
  (`OutputDamageTracker` + buffer age), в `submit()` уходит именно он.
- Кадр запрашивается по факту изменений: коммит клиента, движение мыши,
  смена курсора, изменение размера — всё ведёт к одному `request_redraw()`.

## Запуск

```sh
cargo run -- -c foot              # внутри запустится foot
cargo run                         # просто пустая сессия
RUST_LOG=debug cargo run          # подробный лог
RUST_LOG=mriya_wm=trace cargo run # совсем подробно (каждый кадр, клавиша)
cargo test                        # юнит-тесты (разбор конфига и хоткеев)
```

Сокет печатается в лог (`Mriya WM is ready socket=wayland-N`). Процессы,
запущенные самим композитором через `--command`, получают правильный
`WAYLAND_DISPLAY` автоматически. Для запуска вручную из другого терминала:

```sh
WAYLAND_DISPLAY=wayland-N foot
```

Завершить сессию: `Mod+Esc` (во вложенном режиме это `Alt+Esc`) или закрыть окно
композитора в родительской сессии.

## Горячие клавиши

| Комбинация | Действие |
|---|---|
| `Mod+ЛКМ` + перетаскивание | переместить окно |
| `Mod+ПКМ` + перетаскивание | изменить размер (правый нижний угол) |
| `Mod+q` | попросить активное окно закрыться |
| `Mod+m` | развернуть/восстановить окно |
| `Mod+f` | полноэкранный режим окна |
| `Mod+Return` | запустить `foot` (из дефолтного конфига) |
| `Mod+Esc` | завершить сессию композитора |

Дефолтные привязки ставятся, только если в конфиге нет секции `binds`; всё
остальное задаётся в `binds` (см. [example-config.kdl](example-config.kdl)).

Клик по окну поднимает его и передаёт фокус. Клиентские запросы на
move/resize (из CSD) тоже обрабатываются.

Во вложенном режиме `Super`-хоткеи сначала видит родительский композитор:
если там занято `Mod+q`, до нас эта комбинация не дойдёт.

## Решения, которые стоит помнить

- **`Space<Window>` из Smithay** используется как модель стека окон: позиция +
  порядок наложения. Для стекинг-WM (цель проекта) это ровно то, что нужно;
  тайлинг, если появится, будет надстраиваться сверху.
- **Бэкенд живёт в состоянии** (`Mriya::renderer`), а не в замыкании
  источника событий winit. Иначе `request_redraw()` нельзя вызвать из обработки
  коммитов, и содержимое клиента не перерисовывается до следующего события winit.
  `render_frame()` на время кадра забирает бэкенд из состояния, чтобы не
  бороться с borrow checker.
- **Один `bind` → `render` → `submit` на кадр.** Пропускать `submit` при пустом
  уроне нельзя: damage tracker и buffer age считают, что каждый рендер
  соответствует свопу, и после пропуска он думает, что на экране уже новое
  содержимое.
- **Флаш клиентов — раз за итерацию событийного цикла**
  (`EventLoop::run(..., |state| state.flush_clients())`), а не только в источнике
  Wayland. События ввода рождаются в источнике winit, и без отдельного флаша
  клавиши/кнопки залипали в буфере до следующего запроса клиента.
- **`WAYLAND_DISPLAY` переопределяется только после инициализации winit**,
  иначе бэкенд подключился бы к нашему же ещё не работающему сокету.
- **Курсор**: именованные курсоры — `MemoryRenderBuffer` из XCursor-иконки
  (кэш по имени и размеру, `Fourcc::Argb8888`, hotspot из файла),
  клиентские — `WaylandSurfaceRenderElement` (hotspot из `CursorImageAttributes`).
  Оба варианта идут в кадр как custom-элементы `render_output`.
- **Damage tracker** создан с `from_output`, поэтому сам следит за размером и
  трансформацией вывода; после ресайза окна два кадра рисуются полностью
  (`full_redraw`), потому что содержимое буфера не определено.
- **Порядок элементов для damage tracker — сверху вниз.** `render_output`
  рисует срез в обратном порядке, поэтому список собирается «снизу вверх»
  (рамка ниже своего контента, окна в порядке стека, курсор сверху) и затем
  переворачивается. Если забыть про это, фон рамки закрашивает содержимое —
  ошибка уже была поймана на этапе A.
- **Рамка привязана к контенту, а не наоборот.** `Space` хранит позицию
  контента; рамка — вычисляемая надстройка (`FrameGeometry`), поэтому
  конфигурационные размеры для клиента и математика ресайза остаются простыми.
- **Хоткеи не зависят от раскладки**: кроме клиентского keymap собирается
  второй (`rules=evdev`, `layout=us`), и привязки сравниваются с его
  keysym для нажатого keycode. Иначе `Mod+t` перестаёт работать при включённой
  русской раскладке. Подавление повторов при этом ведётся по keycode.
- **`binds` — данные, а не код**: парсер отдаёт `Vec<Binding>` с действиями,
  исполняет их `Mriya::run_action`, поэтому новые действия добавляются в двух
  местах (парсер + исполнение), а не раскиданы по обработчикам ввода.

## Ограничения текущей итерации

- Анимированные курсоры не поддерживаются: берётся первый кадр иконки.
- Размер курсора — `XCURSOR_SIZE` без масштабирования под fractional scale
  (масштаб вывода пока всегда 1.0).
- `wl_cursor` поверхностей от клиентов (server-side cursors) нет: клиенты
  рисуют курсор сами, мы его только композитим и скрываем свой.
- Нет `layer-shell`, `xdg-activation`, `primary-selection`, `fractional-scale`,
  `text-input`, XWayland.
- В рамке нет иконки приложения (нужен поиск по app-id → .desktop → тема
  иконок).
- Палитра — встроенный пресет: в xfwm4 эти 24 цвета берутся из GTK-темы,
  поэтому оттенки могут отличаться от сессии XFCE. Переопределяется в
  `decorations { palette { ... } }`.
- Классическая тема `Default` сама красит боковые границы активного окна
  цветом `inactive_color_2` (так в её XPM), поэтому у активных окон боковины
  серые — это поведение темы, а не ошибка.
- Из кнопок рисуются только те, для которых есть действия: close, maximize,
  hide (hide пока ничего не делает). `menu`/`shade`/`stick` пропускаются.
- Автоперезагрузки конфига нет: правки применяются после перезапуска.
- Из niri-конфига пока не реализованы `layout`, `output`, `window-rule`,
  `prefer-no-csd`, `animations`, настройки устройств ввода (им нужен libinput,
  т.е. TTY-бэкенд).
